The only warnings are the 14 that were already there (starlette/httpx, skl2onnx); none say "never retrieved" and none are unraisable-exception warnings.

**What changed**
- **One read per request:** `check` now returns today's spend, in the `BudgetLedger` Protocol and in both ledgers. `InMemoryLedger` computes it under its lock. `DynamoLedger` returns the value from the single `GetItem` it already does for the cap check. `spent_today` stays in the ledgers' public API, but the pipeline no longer calls it.
- **Quota stage:** the spend now comes straight from `check`, and the separate `spent_today` read is gone.
- **Ledger writes:** `record` now runs through `loop.run_in_executor`, so it never blocks the event loop.
  - Each write goes into a `pending` set that holds a strong reference and removes the future when it finishes.
  - A done-callback, `_log_record_failure`, always reads the future's result and logs any error as a warning. It never raises.
  - Nothing is awaited inside `account`, so it is safe on the cancellation path.
- **End of pipeline:** the wait happens in `finally`, before `Done`, but only when the task is not being cancelled.
  - It is `if pending:` then `asyncio.wait(set(pending), timeout=settings.stage_timeout_s)`. The empty-set guard avoids a `ValueError`, and `wait` itself never raises on timeout.
  - If a cancellation arrives during that wait, `Done` is still emitted and then `CancelledError` is raised again.
  - When the LLM deadline is exceeded, `asyncio.timeout` clears the cancellation, so that path still waits, which is correct.
- **`container.py`:** I rewrote the comment above `_TIMEOUTS` to describe the new behaviour.

**Tests**
- `check` returns today's spend, for `InMemoryLedger` and for `DynamoLedger` under moto. The Dynamo test counts reads with the botocore hook `before-call.dynamodb.GetItem` and expects exactly one.
- A ledger whose `spent_today` raises doesn't break the pipeline, and the quota span's `spent_today_usd` comes from `check`.
- `record` runs on a thread other than the event loop's (the test from the task).
- Added beyond the task:
  - On cancellation, `Done` is emitted without waiting for a blocked write, and the write still finishes afterwards.
  - With a stuck ledger, a normal run still completes, bounded by `stage_timeout_s`.
- The failing-write test now also checks that the `RuntimeError` is logged.
- `test_client_disconnect_still_bills_generated_tokens` now polls every 0.01 s for up to 2 s instead of reading the ledger immediately.

**Deviations from the plan**
- The plan said to wait "after `output_guard`". I put the wait in `finally` so it also covers blocked or error endings and the deadline path, and I used `task.cancelling()` to skip it on real cancellation.
- The two existing spy ledgers in `test_pipeline.py` now return a float, to match the new `check` signature.
- The polling loops need `# noqa: ASYNC110` for ruff.

**Self-review**
- If the event loop has already closed when a write finishes (tests that end after a cancel), asyncio drops the result safely, and the thread pool is waited for at shutdown.
- Git warns about LF→CRLF when staging these files; the diff is still limited to the actual changes.

## What I checked, by focus area

1. **Token usage**
   - **Bedrock:** events arrive as `messageStop` then `metadata`, so `stop_reason` is set before usage is sent, and the pipeline reads the stream to the end, so usage is always collected.
   - **Ollama:** usage comes from the `done` chunk.
   - **Cost:** the math is right.
   - **Fallback chain:** each attempt is billed separately. Failed attempts go through `except Exception`, cancellation goes through `except CancelledError` and re-raises, and `Done` shows the total across attempts.
   - **Deadline:** when `llm_deadline_s` expires, the timeout is converted to `TimeoutError`, so `_cancelling()` is 0 and the pending writes are awaited. This is correct.
2. **Ledger**
   - **Normal path:** the order is: ledger writes awaited (up to `stage_timeout_s`), then `Done`, then `flush`, then `None`, then the response closes. So writes finish before the response ends unless DynamoDB is slower than 10 s.
   - **Visitor disconnect:** `app.py` `stream()` cancels the task without waiting for it. A write in progress can therefore be frozen, and it will usually finish when the environment is next thawed. This was already true for `flush`. It is acceptable: the amount at stake is small, the per-visitor limit caps it, and generation is also cut off.
   - **Hang risk:** none. The wait has a timeout, and a cancellation during the wait is re-raised after `Done` is emitted. Using `task.cancelling()` this way is correct on Python 3.12.
3. **Privacy:** no visitor-supplied text reaches spans or SSE attributes. Spans record only the exception type name. `model_len` replaces the raw model id. Provider errors (the `LLMError` text, the Ollama error that includes the httpx message) are never recorded. `stop_reason` values come from the provider's fixed list.
4. **Telemetry refactor:** behavior is unchanged. `headers=None` and `session=None` give the same defaults as before. The endpoints, the SigV4 `xray` service and region, and the 2 s timeout are all the same.
5. **Strict config:** `load_settings` uses `include_input=False`, so error messages name the key but not its value. `Settings.model_validate` still prints `input_value` if called directly, but only tests do that.

## Minor

1. **A missing Bedrock usage field makes a good answer count as a failure.** At `src/ask_my_cv/aws/bedrock.py:69`, `usage["inputTokens"]` raises `KeyError` if the field is missing. That happens after all the text has arrived, so the pipeline marks the provider as failed, falls back and bills twice.
   - Fix: read the fields with `.get(...)` and send usage only if both are integers.
2. **A stream with usage but no text no longer falls back.** At `src/ask_my_cv/pipeline.py:99-104`, a stream that yields only `TokenUsage` now returns an empty answer. Before, `StopAsyncIteration` triggered a fallback. It has no effect in prod (the chain is Haiku only) but it changes behavior in dev.
   - Fix: after the loop, `if not parts: raise LLMError(...)` inside the `try`, so the failed attempt is still billed.
3. **A stale `stop_reason` can remain on the span.** At `pipeline.py:201`, if a failed attempt reported usage and the final attempt did not, the span shows `usage_source="estimated"` with the earlier attempt's `stop_reason`.
   - Fix: `st.set(usage_source="estimated", stop_reason="")`.
4. **Input tokens are not billed when an attempt ends before any output.** At `pipeline.py:193`, a first-token timeout or a disconnect before the first chunk bills nothing, even though Bedrock has already read the prompt. The early `return` was already there, but it goes against the goal of billing on the provider's token counts.
   - Fix: bill `estimate_tokens(system + user)` as input whenever the call was made.
5. **A ledger write that outlasts the wait is lost silently.** At `pipeline.py:245`, there is no log when writes are still unfinished after the timeout. DynamoDB can take longer than the 10 s wait: 3 attempts × (2 s connect + 3 s read), plus backoff.
   - Fix: `_, not_done = await asyncio.wait(...)`, then `if not_done: logger.warning("registre: %d écritures non terminées", len(not_done))`.
6. **The worst-case request time is close to the Lambda timeout.** Adding up quota (10) + embedding/retrieval (up to 10 each) + LLM (25) + ledger wait (10) + flush (2) gives about 57 s against a 60 s timeout (`infra/prod/lambda.tf:83`).
   - Fix: wait for the ledger with a shorter, dedicated timeout (for example 3 s) instead of `stage_timeout_s`.
7. **The Langfuse token could appear in logs.** At `src/ask_my_cv/telemetry.py:23`, `ExporterConfig.headers` holds the Basic Langfuse token, and the dataclass's default `repr` would print it if the object is ever logged.
   - Fix: `field(default_factory=dict, repr=False)`.
