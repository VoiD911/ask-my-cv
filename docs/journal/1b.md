## Stage 2 issues

**Critical (a plan defect, blocks Task 5): the served ONNX model does not compute what scikit-learn computes.** There are two separate conversion bugs, found by comparing the TF-IDF vectors:
1. **`sublinear_tf`:** skl2onnx (`operator_converters/tfidf_transformer.py`) builds `log(tf+1)`, but scikit-learn computes `log(tf)+1`. Measured: every n-gram that appears twice is off by a factor of exactly 0.936, which is ln3/ln2 compared with 1.693/1. Even clean ASCII text differs by up to 0.015.
2. **Whitespace:** scikit-learn's `char` analyzer collapses runs of 2+ whitespace characters (`\s\s+`) into one space, and ONNX does not. Texts containing `\r\n` are the worst cases (0.0545).

Measured on the real data:

| Configuration | Parity max diff | Gate |
|---|---|---|
| As implemented | 0.0545 | fails |
| sublinear on, whitespace normalized | 0.0152 | fails |
| sublinear off, whitespace not normalized | 0.0521 | fails |
| **sublinear off + `re.sub(r"\s\s+", " ", t)` applied to every text** | **0.00000** | **passes** (recall 0.85, FPR 0.00, Gandalf 0.9794, adversarial 100%) |

The unit tests miss this because the tiny data has almost no repeated n-grams and no whitespace runs.

Recommended fix, which changes a plan fact and so needs your approval:
- Set `sublinear_tf=False` in both `build_pipeline` and `HYPERPARAMS`.
- Add one shared `normalize_text()` function. Apply it in `fit`, in `evaluate` (every eval and adversarial text), and later in `OnnxDetector` in Task 6, because the served model receives raw text.
- Update the plan's measured-facts section and the `HYPERPARAMS` test to match.
- Add a unit test with a repeated n-gram and a `\r\n` text, so parity is actually exercised.

The alternative is to keep `sublinear_tf` and patch the exported graph to compute `Where(tf>0, Log(tf)+1, 0)`. That is more complex.

**Important: the export is not deterministic across processes.** On the real data I got 3 different sha256 values across separate processes (`c5f2…`, `da6e…`, `25dc…`). The fitted model is identical every time (vocabulary, idf, coefficients and scores all match). The only difference is the order of `ModelProto.opset_import`, which skl2onnx builds from a set whose order depends on the per-process hash seed. As a result, `model_sha256` in `metrics.json` and the model card changes from run to run. That contradicts "entraînement déterministe" and "reproductible", and `test_export_is_deterministic` can't catch it because it runs in a single process. Fix in `to_onnx_bytes` before serializing:
```python
ops = sorted(model.opset_import, key=lambda o: o.domain)
del model.opset_import[:]
model.opset_import.extend(ops)
```
I checked this with 6 different `PYTHONHASHSEED` values: all 6 gave the same sha256. Also add a test that runs the export in 2 subprocesses with different `PYTHONHASHSEED` values and compares the bytes.
