**Objectif :** à chaque PR, des évaluations déterministes (promptfoo, faux LLM) prouvent les garanties du pipeline ; chaque nuit, une red team et des évaluations sur le vrai modèle frappent l'API **déployée** via CloudFront, la dérive du classifieur est mesurée (PSI) sur les scores de production, et tout échec ouvre une issue GitHub. Le classifieur passe en v1.2.0 (attaques « répéter / recopier ce qui précède ») avec un histogramme de référence du domaine.

**What changed:**
- **Config** (`settings.py`): two new fields, `eval_token` (default `None`, hidden from repr) and `eval_limit_per_window` (default 300, must be at least 1). The `EVAL_TOKEN` env variable fills `eval_token`. A new check raises an error if the token is empty, or shorter than 32 characters in prod. Through `load_settings` that becomes a `ConfigError` whose message never contains the value. `settings.aws.yaml` now sets `eval_limit_per_window: 300`.
- **Secrets** (`secrets.py`): `OPTIONAL_SECRET_NAMES = ("EVAL_TOKEN",)` is loaded from SSM when present. When it's absent there's no error, and the three existing secrets are still required.
- **Ledgers** (`budget.py`, `aws/dynamo.py`): `check(visitor, now, limit=None)` works the same way in the Protocol, `InMemoryLedger` and `DynamoLedger`. The daily spend cap is checked before the quota, whatever `limit` is. In `DynamoLedger`, `:limit` now uses the passed limit.
- **Pipeline** (`pipeline.py`): new `evaluation: bool = False` parameter. When it's true, the quota check uses `eval_limit_per_window`, and the `quota` and `injection` stages get `eval=True`, which becomes the span attribute `xops.eval`. Normal requests don't get the attribute at all.
- **App** (`app.py`): `_is_eval()` returns false if the token isn't configured or the header is missing or empty. Otherwise it compares the two values as UTF-8 bytes with `hmac.compare_digest`. A valid token sets `visitor = "eval"`, a constant that can't collide with a real visitor ID (those are 16-character hex strings), and passes `evaluation=True`.

**New tests:** the app tests cover every case in the task. They also check that an eval request doesn't use up the client IP's own quota. The privacy test now has two eval cases, puts the token in its forbidden list, and checks every SSE event for the token. There are ledger tests for `limit` (both ledgers, including the spend cap still applying), SSM tests for the optional token, and config tests (defaults, env override, repr, empty token, bound, the short prod token without leaking it, and the aws yaml).

**Deviations from the task:**
- An empty token (`""`) is rejected in every environment, not just prod. Without this, an empty configured token would have matched a missing header. An empty `EVAL_TOKEN` env variable is treated as not set.
- The comparison encodes both values to bytes before `compare_digest`. Comparing strings raises `TypeError` on non-ASCII header values, which would have been a 500. A test sends a non-ASCII header and checks for a 200 answered as an ordinary visitor.
- The pipeline only passes `limit=` on eval requests; normal requests keep the old call. I added `limit: int | None = None` to the ledger subclasses in `tests/test_pipeline.py` so pyright passes on the override.

**Security self-review:**
- **Constant-time comparison:** yes, on bytes of the same type. The only thing that leaks is the token's length, and `compare_digest` accepts that.
- **Token never leaked:** it isn't in the repr, spans, SSE events or config error messages, and nothing logs it. Tests check all of this.
- **No oracle:** a wrong, missing or empty token takes exactly the ordinary path, with the same message and status. The response doesn't reveal whether a token is configured.
- **No bypass:** the spend cap is checked before the quota in both ledgers, so the eval path can't get past it. Tests confirm this at the ledger, pipeline and HTTP levels.
- **No new abuse route:** all eval traffic shares one "eval" bucket with its own bounded limit (≥ 1, 300 in prod), and the request body size limit and validation still apply. Without the token, nothing changes.
- **CORS:** `allow_headers` still only lists `content-type`, so browsers can't send `X-Eval-Token` cross-origin. That's intended, since the header is for server-side evals.

The edit scripts I used are in the scratchpad (`1d3/t1_edit.py`, `1d3/t1_tests.py`) and are not in the repo.

**Final Logs Insights query (`ml.drift.LOGS_INSIGHTS_QUERY`):**
```
filter name = "injection" and not isPresent(attributes.`xops.eval`)
| fields attributes.`xops.score` as score
| limit 10000
```
Rationale from the real span sample (`{"name": "injection", "attributes": {"xops.score": 0.083, ...}}`): Logs Insights auto-discovers nested JSON fields via dot notation, but since the attribute's own key (`xops.score`) contains a literal dot, that segment must be isolated in backticks (`` attributes.`xops.score` ``) so it isn't parsed as an extra nesting level. Same escaping used for `xops.eval` to exclude eval traffic.

**Implementation summary:**
- `psi(reference_counts, production_counts)`: proportions with `EPSILON = 1e-4` smoothing added to both sides before the PSI log term; raises `ValueError` on length mismatch.
- `histogram(scores)`: `numpy.histogram` with 10 bins on `[0, 1]` (1.0 falls in the last bin via numpy's inclusive-right-edge behavior on the final bin).
- `fetch_scores(client, log_group, start, end, poll_interval=2.0, max_polls=30, sleep=time.sleep)`: `start_query` then polls `get_query_results` (`Running` → sleep+retry, `Complete` → parse rows, `Failed`/timeout → raises `DriftError`). `sleep` is injectable for fast tests.
- `main(argv, client_factory=..., fetch_scores=...)`: boto3 `logs` client built lazily only when `main` runs (not at import time); reads `--reference` JSON's `domain_score_histogram.counts`; `MIN_SAMPLES = 50` → "données insuffisantes" message, exit 0; PSI ≥ 0.2 → message, exit 1; 0.1 ≤ PSI &lt; 0.2 → `::warning::` message, exit 0; else plain message, exit 0. All output in French.

**Deviations from the task sketch:**
- Query uses `` `xops.eval` `` / `` `xops.score` `` backtick-escaping (not the plain-dot form given as a fallback guess in the task file), based on the real captured span's flattened-key structure.
- `MAX_POLLS`/`POLL_INTERVAL_S` are module constants (30 polls × 2s) rather than a fixed wall-clock deadline, to keep the Stubber-based timeout test deterministic and fast (test injects `sleep=lambda _: None`).
- Added an explicit `fetch_scores` injection point in `main` (beyond the required `client` injection) purely to make the `main`-level branch tests (insufficient data / fail / warn / ok) independent of AWS wiring — `fetch_scores` still defaults to the real implementation.

## Minor
1. **Drift can crash on injection spans without a score.** `ml/drift.py:34-38` and `:94`: if the detector raises, the stage records `error` before `score` is set (`stages.py:62-70`). The Logs Insights row then has no `score` field and `_row_value` raises `DriftError`, so drift fails for the next 7 days. Fix: add `and isPresent(\`attributes.xops.score\`)` to the filter.
2. **The drift reference will produce false alarms.** The PSI formula is correct, but the reference is the 50 legitimate domain questions, which almost all score in bin 0. Real attack traffic lands in bins 8-9, where the reference share is only `EPSILON=1e-4`. About 2% of production in bin 9 adds roughly 0.106 to PSI, and 4% or more reaches the 0.2 failure threshold. The alarm would then track attack volume, not model drift. Fix: exclude scores at or above `injection_threshold` from the production histogram, or use add-0.5 (Laplace) smoothing on counts, and raise `MIN_SAMPLES` (for example to 200).
