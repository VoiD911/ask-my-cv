**Changes compared with the task's snippet**
- **Previous image:** the rollback target comes from `Code.ResolvedImageUri` (`repo@sha256:…`), not `Code.ImageUri`. `ImageUri` can be a tag, while `ResolvedImageUri` gives the exact digest to roll back to. If it isn't a digest, the job prints a warning and skips the rollback.
- **Digest check:** after `describe-images`, the job stops unless the digest starts with `sha256:`.
- **Check after rollback:** after `wait function-updated-v2`, the rollback step calls `curl --retry 5 --retry-all-errors "$SITE_URL/api/healthz"`. It doesn't re-run the full smoke test, because that test uses up the IP's hourly quota and would fail.
- **Rollback failures stay visible:** under bash `-e -o pipefail`, any failure turns the step red. It always logs a `::error::` saying the rollback happened, and a separate `::error::` if healthz fails after it. `SITE_URL` reaches the script through `env:`, not inline.
- **Token masking:** I removed an `echo "::add-mask::"` line because semgrep's `unsafe-add-mask-workflow-command` rule flagged it. The ECR token is never printed (no `set -x`, no `echo`), and syft redacts it in its logs.

**What the docs showed (checked against the pinned versions)**
- **amazon-ecr-login v2.1.7:** it just runs `docker login -u AWS -p … <registry>`. Where the credentials end up depends on the runner's Docker config, which the action doesn't guarantee.
- **How cosign authenticates:** its default registry keychain reads `~/.docker/config.json` and any credential helper, so it works as-is on the host after ecr-login.
- **How syft authenticates:** I passed the credentials as environment variables instead of mounting `~/.docker`. In syft v1.52.0, `SYFT_REGISTRY_AUTH_AUTHORITY`, `_USERNAME` and `_PASSWORD` are read in `PostLoad` and take precedence over on-disk config. The values are the registry host (`${ECR_REPOSITORY_URL%%/*}`), `AWS`, and the output of `aws ecr get-login-password`. This doesn't depend on how `docker login` stores its secrets.
- **Why syft reads from ECR:** in `registry:$IMAGE_REF` mode the SBOM describes the exact pushed digest. It also works on a re-run where the image already existed and nothing was built locally, so there's no `docker pull`.
- **cosign v3.1.3 defaults:** on `sign`, `attest` and `verify`, `--new-bundle-format` and `--use-signing-config` are both true by default (bundles are attached through the OCI referrers API). No extra flag is needed. `--type cyclonedx` is a valid predicate type for both `attest` and `verify-attestation`.

**Lint results**

**Risks for the first real run**
1. **Lifecycle policy will expire images faster:** the policy in `infra/bootstrap/main.tf` keeps `tagStatus any, imageCountMoreThan 10`. The signature and attestation are stored in ECR as untagged artifacts, so each deploy adds about 3 entries. The policy would then keep only about 3 deploys, and could orphan or expire referrers or recent images. It's worth adjusting in task 6, for example by counting only tagged images or adding a separate rule for untagged ones.
2. **IAM permissions for referrers:** the referrers API calls may need an ECR permission the role doesn't have yet. I also used `ecr:GetAuthorizationToken` through `get-login-password`, which is already granted. The first run will show whether anything is missing.
3. **Referrers fallback on an immutable repo:** if ECR ever falls back to the `sha256-…` tag scheme instead of the referrers API, pushes would hit the `IMMUTABLE` setting. The fallback in `context.md` (`IMMUTABLE_WITH_EXCLUSION`) still applies.
4. **Large SBOM in Rekor:** the SBOM of the ML image may be several MB and goes into the attestation logged to Rekor. If Rekor rejects it for size, the `attest` step will fail.
5. **Rollback only covers a failed smoke test**, as the task specified. If `update-function-code` succeeds but `wait` fails, nothing rolls back automatically.
6. **Re-runs sign again:** re-running the same commit adds another signature and attestation. That's harmless for verification but adds more lifecycle entries.
