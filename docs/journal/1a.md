   - It costs nothing in 1a (fake and Ollama are free).
   - With Bedrock in 1c, a visitor who disconnects repeatedly can spend tokens that never reach the ledger, which weakens the daily cap. Only the rate limit would still bound it.
   - Suggested fix for 1c: account for the partial text in a `finally` inside the llm stage, for example by raising a `PartialLLMError(provider, text)` from `_stream_llm`.

### Minor

3. **A cancelled stage is logged as `ok`.** When a client disconnects mid-LLM, the probe shows `StageEnd(llm, status="ok")` and `Done(answer_override=None)`, and the span also says `xops.status=ok`. The cause is `stages.py:56`, from an earlier task, which catches only `Exception`. Fix it there:
   ```python
   except asyncio.CancelledError:
       status = "error"; recorder.set(error="CancelledError"); raise
   ```
   Task 12 is not affected, since nobody is reading the queue by then. The damage is to the traces.
4. **The `llm` span says too little when things fail.** When all providers fail, the span only carries `error=LLMError`. It does not say which providers failed, or which one failed mid-stream. Suggested fix: call `recorder.set(failed=...)` before raising at `pipeline.py:69` and `:77`.
5. **The timeout covers the whole stream (`pipeline.py:63`).** A long but healthy Ollama answer that takes more than 20 s is cut off and reported as an error. The llm stage also has no overall deadline: N providers can take N×20 s. `retrieval` has no timeout at all, which will matter with DynamoDB in 1c. The spec says every stage has a maximum duration. A better design would be a time-to-first-token timeout for fallback plus one overall deadline for the stage.
6. **Anything a provider raises that is not an `LLMError` skips fallback.** For example, Ollama's `json.loads` failing on a malformed line (`llm.py`), or a botocore error from the 1c Bedrock provider. The whole request becomes an error. The Bedrock provider must wrap all its errors in `LLMError`.
7. **The ledger checks the budget and records spend in two separate steps (`pipeline.py:105` vs `141`).** Concurrent requests can therefore overshoot the cap. That is acceptable, but note it for the DynamoDB ledger in 1c.
8. The spec asks for embedding to fall back to another provider (§3, step 4); it has no fallback. This is a plan gap, not an implementation gap.

## Security posture (item 3 of the brief)

**Visitor salt.** The default `visitor_salt: change-me` is not exploitable today. The hash is only an in-memory ledger key and is never emitted, logged or stored. It becomes a real issue in 1c: once the hash is stored in DynamoDB, a known salt plus the 2^32 IPv4 space makes it trivially reversible, and an IP counts as personal data under GDPR. Tracked below for 1c.

**Raw IPs in access logs.** uvicorn's access log writes client IPs in clear (`127.0.0.1:60207 - "POST /ask"`), which conflicts with the privacy section of spec §3.

**SSE exhaustion.** Bounded per IP by the quota and by the 20 s stage timeout. Blocked-at-reception requests are cheap and don't count against quota. That's acceptable apart from I3.

**Tracked follow-ups vs actual severity.** None are more severe than tracked, with one nuance: "raw answer streamed before the output guard" and "visitor identity behind a proxy" also apply to the portable compose/VPS path, not just AWS. Keep in mind that 1a must not be exposed publicly as-is.
