**What I checked and found correct**

The outer `except Exception` in `run_pipeline` (src/ask_my_cv/pipeline.py:206) then sets `ERROR_MESSAGE`, so the LLM stage never runs. The test's `llm.calls == 0` check confirms this.
- **What happens to the thread after a timeout:** acceptable. The worker thread can't be killed, so the boto3 call finishes on its own. With the dynamodb client config (connect 2s, read 3s, 3 attempts, src/ask_my_cv/container.py:18), that takes up to about 15–20s per call, and `check` makes two calls. Any late result or exception is dropped harmlessly. One side effect is fine: if the timeout fires after `update_item` succeeded, the visitor's rate counter goes up for a request that failed. That is conservative.
- **The lock:** there is no deadlock. `check` calls the unlocked `_spent`, and the lock is never held across I/O. `check` is now atomic (read the limit, then append), which fixes the real race where two concurrent `check` calls could both get past the limit. The spend total can still change between `check` and `spent_today`, but that value is only used for telemetry, so it's harmless.
- **Test flakiness:** low. 0.1s vs 0.5s leaves a 5x margin. The sleeping thread is joined when the default executor shuts down at loop teardown, so the test costs about 0.5s but doesn't leak anything.

**Important**

1. **`ledger.record` still runs synchronous boto3 on the event loop** (src/ask_my_cv/pipeline.py:176, inside `account`). This is the same bug the commit fixes, left on the per-request cost path. It is called once per provider attempt, including from the `CancelledError` handler at pipeline.py:96. In production that's up to about 15s of blocked event loop per call when DynamoDB is slow. It also contradicts the goal of the commit.
   - **Fix:** don't await it; hand it to the executor and keep a reference to the future, e.g. `asyncio.get_running_loop().run_in_executor(None, deps.ledger.record, provider.id, cost, ts)`.
   - **Log errors in a callback:** attach a done-callback that logs failures the same way the current `except` does.
   - **Why not await:** awaiting would work on the normal path, but awaiting inside the `CancelledError` handler can be interrupted by a second cancel, and the cost would never be recorded.

**Minor**

2. **The thread-safety test doesn't prove the lock** (tests/test_budget.py:37). Because of the GIL, `self._spend[d][p] += x` almost never loses an update, so the test very likely passes without the lock too. The race that actually matters is `check` for one visitor across threads.

That executor is shared with `DynamoVectorStore.search`, `BedrockEmbedder` and telemetry flush. During a DynamoDB outage, a burst of requests could queue up behind it. The fast-fail botocore timeouts already limit this. If it needs more protection, a dedicated small `ThreadPoolExecutor` for the ledger would contain it.

## Review of commit ec69345 (SSM secrets loader)

**Verdict: Approved.** I found nothing Critical or Important. I ran `tests/test_secrets.py` with the venv python and all 4 tests pass. I changed no files.

### What checks out
- **Fails closed.** Any error from boto or SSM propagates out of `create_app` and startup aborts. This covers AccessDenied, missing KMS permission, timeouts, and a bad `Path`. It also covers a prefix of `"/"`: `rstrip` turns it into `""`, which raises a parameter validation error.
- **No secret values in error messages.** Boto errors name the operation and the `Path`, never the parameter values. Nothing in `secrets.py` logs or formats a value. `load_settings` already uses `include_input=False`, so the salt never appears in a `ConfigError`.
- **Path handling is correct.** `Recursive` defaults to False, so only direct children of the prefix are read and nested paths are ignored. `rsplit("/")[-1]` plus the allow-list on `SECRET_NAMES` is correct for that. The boto paginator handles the 10-results-per-page limit and empty pages that still carry a NextToken.
- **Missing secrets are still caught later.** If the prefix is set but the parameters are missing, the loader stays silent, but startup still stops downstream:
  - the Dockerfile sets `ASK_ENVIRONMENT=prod`, so the salt validator rejects the default `"change-me"`;
  - `settings.aws.yaml` enables `tracing: [..., langfuse]`, so `telemetry.py` refuses to start without the keys.
- **Explicit env wins, even when empty.** `setdefault` won't overwrite an existing variable, even an empty one. `load_settings` then skips the empty value (`if value :=`), falls back to `"change-me"`, and the prod validator rejects it.
- **Tests can't reach real AWS.** `mock_aws` plus the autouse fixture in `conftest.py` (fake credentials, empty config files, `AWS_PROFILE` removed) keeps the tests off AWS. The client is injected, so the tests never build a real one.

### Minor
1. **`src/ask_my_cv/secrets.py:29` – retry setting.** `retries={"max_attempts": 2}` means 2 *retries*, so 3 attempts in total. The worst case is about 3×(2+3)s plus backoff, roughly 15s or more. That is longer than Lambda's 10s init-phase limit, so a cold start slows down (Lambda re-runs init inside the first request). It is still fail-closed. Fix: `Config(connect_timeout=2, read_timeout=3, retries={"total_max_attempts": 2, "mode": "standard"})`.
2. **`secrets.py:45-46` – missing secrets depend on other code.** Rejecting absent secrets relies on settings and tracing config elsewhere. If someone later removes `langfuse` from `tracing`, or runs with `environment: dev` and a prefix set, a typo in the prefix passes silently. Fix: once the prefix is set, fail if a name is neither in `env` nor returned by SSM. Name only the missing *names* in the message:
   ```python
   missing = [n for n in SECRET_NAMES if n not in values and not env.get(n)]
   if missing: raise ConfigError(f"SSM {prefix}: paramètres absents : {missing}")
   ```
3. **Tests don't cover the fail-closed intent** (`tests/test_secrets.py`). Nothing checks that an SSM error propagates. Add a test where `client_factory` returns a client whose paginator raises `ClientError` (or use moto with a prefix of `"/"`), and assert `pytest.raises`. Also add:
   - a test with more than 10 parameters, to exercise pagination;
   - a test with a nested `/ask-my-cv/x/VISITOR_SALT`, to confirm it is ignored.
4. **`secrets.py:28` – region lookup.** Only `AWS_REGION` is read. Lambda always sets it, but locally and in the tests' conftest only `AWS_DEFAULT_REGION` is set. Fix: `os.environ.get("AWS_REGION") or os.environ.get("AWS_DEFAULT_REGION") or "ca-central-1"`. `_ssm_client` itself has no test coverage; a one-line test checking `client.meta.region_name` would do.
5. **Leak through debug logging.** botocore logs full response bodies at DEBUG level, which would include the decrypted `Value`s. No logging config in the repo enables that today. Keep the root and `botocore` loggers at INFO or above in prod, for example with `logging.getLogger("botocore").setLevel(logging.INFO)` at startup.
6. **Putting secrets in `os.environ` is acceptable here.** Subprocesses inherit it and it is readable in `/proc/self/environ`, but this is a single-purpose Lambda that runs no untrusted subprocesses. `telemetry.py:37-38` already reads the keys from the environment, and the values never show in the Lambda console or config. That is better than plain Lambda env vars. The cleaner option is to return the dict and pass it into `load_settings` and `configure_tracing` (keys stored as `SecretStr`). That is optional and not needed for this commit.
7. **Stale comment in `settings.aws.yaml:1-2`.** It still says the secrets come "par variables d'environnement". Mention `ASK_SSM_PREFIX` and the SecureString parameters there. Also note, outside this repo, that the Lambda role needs `ssm:GetParametersByPath` on `arn:...:parameter/ask-my-cv` and `/ask-my-cv/*`, plus `kms:Decrypt` on the key (the `aws/ssm` default key needs no extra grant).

## Important

**I1. POST /ask through CloudFront will fail signature validation with 403 unless the client sends `x-amz-content-sha256` (cdn.tf:13-18, cdn.tf:65).**
- Lambda OAC doesn't support unsigned payloads. For POST and PUT, the viewer must send the hex SHA-256 of the body in `x-amz-content-sha256`. CloudFront doesn't compute it.
- GET /healthz and /models will work, so a smoke test on GET will hide the problem.
- Fix, on the frontend (plan 1e) and in any curl or smoke test:
  ```js
  const body = JSON.stringify({question, model});
  const buf = await crypto.subtle.digest("SHA-256", new TextEncoder().encode(body));
  const hash = [...new Uint8Array(buf)].map(b => b.toString(16).padStart(2, "0")).join("");
  fetch("/api/ask", {method: "POST", body, headers: {"content-type": "application/json", "x-amz-content-sha256": hash}});
  ```
- The body must be byte-identical to what was hashed.
- If the frontend is ever cross-origin, also add `x-amz-content-sha256` to `allow_headers` in src/ask_my_cv/app.py:68. The managed origin request policy already forwards the header.
